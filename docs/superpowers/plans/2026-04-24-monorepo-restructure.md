# Monorepo Restructure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Convert the single-package `ts-libghostty-vt` repo into a Bun-workspaces monorepo where the existing binding lives at `packages/libghostty-vt/`. No API changes; the existing 207 smoke tests must continue to pass at the new paths. Sets the foundation for Pass 4 (KeyEncoder) and Pass 5 (`blinkyterm`).

**Architecture:** Bun workspaces with `workspaces: ["packages/*"]` in a private root `package.json`. Files move via `git mv` to preserve history. The FFI loader's package-root resolution (`src/ffi.ts:resolvePackageRoot`) walks `..` from `src/` and continues to find `prebuilds/` correctly because the binding's `src/` and `prebuilds/` move together. Build scripts use `ROOT="$(cd "$(dirname "$0")/.." && pwd)"` patterns that adapt automatically. `tsconfig.json` splits into `tsconfig.base.json` at root + per-package `tsconfig.json` that extends it. The npm package name renames from `ts-libghostty-vt` to `libghostty-vt` (the package was never published, so this is a free rename).

**Tech Stack:** Bun 1.3.13 (workspaces), TypeScript 5.x, existing FFI infrastructure (libghostty-vt.dylib + Bun FFI).

## Pre-execution context

**Where the work happens:** This plan is executed in the existing repo (currently at `/Users/mw/Code/prime/ts-libghostty-vt/`, on `main`). The repo directory itself is not renamed by this plan — that's a separate post-merge step (see Task 14). All Git operations happen in this single working tree.

**Known hazards:**
- The `dist/` directory may exist with stale build output — it should NOT be moved with `git mv`; it gets regenerated by `bun run build:ts`.
- `bun.lock` regenerates after workspace conversion. Don't try to preserve the old one.
- `node_modules/` is gitignored; it'll be wiped and recreated.
- The `.tmp/` directory holds build/probe scratch — gitignored, ok to leave alone or wipe.

**Verification mental model:** This is a structural refactor with zero API changes. The "test" for each task is "after this change, the previously-passing tests still pass at the same count." The Task 1 baseline file is the source of truth; later tasks compare against it.

### Task 4: Create workspace root `package.json`

**Files:**
- Create: `package.json` (at workspace root, private, declares workspaces)

The root needs its own `package.json` declaring workspaces. This package is private (never publishes); it just glues things together for `bun install`.

- [ ] **Step 1: Write the root package.json**

Create `/Users/mw/Code/prime/ts-libghostty-vt/package.json` with this exact content:

```json
{
  "name": "ts-libghostty-monorepo",
  "private": true,
  "version": "0.0.0",
  "type": "module",
  "workspaces": [
    "packages/*"
  ],
  "engines": {
    "bun": ">=1.3.13"
  },
  "devDependencies": {
    "@types/bun": "latest",
    "typescript": "^5.4.0"
  }
}
```

Notes on each field:
- `name: "ts-libghostty-monorepo"` — distinguishes from any package; the trailing `-monorepo` suffix signals "this is a workspace root, not something you publish"
- `private: true` — Bun and npm refuse to publish a package with `private: true`. Belt-and-suspenders.
- `version: "0.0.0"` — required by package.json schema; meaningless for a private workspace root
- `type: "module"` — match the package
- `workspaces: ["packages/*"]` — Bun's workspace discovery glob
- `engines.bun` — same minimum as the binding
- `devDependencies` lifted from the original root for hoisting; both packages will share these

- [ ] **Step 2: Remove the now-stale top-level `bun.lock`**

```bash

```

It's stale because it reflects the old non-workspace layout. `bun install` in Task 9 will regenerate it as a workspace lock.

- [ ] **Step 3: Commit**
